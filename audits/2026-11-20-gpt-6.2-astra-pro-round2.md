# `git-buttress` v0.3.0 — formal contract and correctness review, round 2

**Revision:** `d7e7ad0f8176f87133afab4b4bcc81887c4e224b`. **Decision:** The canonical digest calculations pass independent checks. The automatic hook, wrapped `git fsck`, signing path, and installer do **not** yet meet their end-to-end guarantees. Do not use a successful automatic operation alone as a release gate.

The most important fixes since round 1 are real: the tag target is no longer last-header-wins; a plain tip no longer suppresses verification of available sealed ancestors; explicit/name pins disable shallow skips; signing and autotagging no longer load the disk cache; and hook stdin is no longer truncated at the first non-UTF-8 record. Remaining high-priority failures concern *which refs and edges were checked, which operation was signed or published, and which Git behavior was displaced*. None requires a defect in BLAKE3.

## Priority findings and release implications

### High

1. **Standalone `fsck` can still give a clean result on an incomplete ref listing.** `src/hooks.rs:1195–1216` now propagates nonzero child status and preserves ordinary refname bytes. But `for-each-ref` is an iterator over reportable refs, not a ref-database consistency check. Git's `ref-filter.c:3013–3023` *warns and omits* broken names/refs; the files iterator can also omit dangling symrefs (`refs/files-backend.c:1017–1033`). Successful stderr is not inspected here. Every error distinguishing detached HEAD, unreadable HEAD and an unborn branch is discarded by `if let Ok((None, ...))`. The final count (`src/hooks.rs:1284`) can therefore account for every **returned** row and still not account for every required ref. This is distinct from the now-fixed “nonzero means empty” bug. **Fix:** validate the ref database (e.g. version-appropriate `git refs verify` plus explicit dangling/HEAD handling), require complete enumeration of a specified set, and handle unborn HEAD as a specific valid state, not a blanket error exemption. A stock fsck before wrapped fsck is useful but does not make standalone fsck exhaustive.

2. **Coverage is lost between verifier, hook, pin issuer and CLI.** `pinned_expect` is captured **before** tag peeling; adding a trailer changes `expect` but not this flag (`src/protocol.rs:929–930,952–966,1013–1014`). Explicit and ref-name pins are strict; a trailer-only pin isn't. A missing parent at a marked sealed boundary can yield `Match { shallow_stops > 0 }`; `NoEvidence` has *no field* for those stops even when ancestors were skipped (`:861–874,1122–1141,1166–1186`). `check` labels a partial `Match`, and strict missing policy rejects it, but `fsck` counts it as verified under silent **and warn**, and prepared silently accepts it under those policies (`src/main.rs:320–375`; `src/hooks.rs:624–635,1244–1255`). An `Incomplete` from a trailer-bearing tag is tolerated in prepared if there is no **name** pin and policy isn't strict (`src/hooks.rs:671–688`). Autotag accepts either successful outcome with `allow_shallow=true`, discards coverage and exempts its own create from verification (`:731–763,512–540`): it can mint a pin which the strict name-pin reader cannot fully check there. An unrelated early missing object can also stop the walk before a different seal is compared. `BUTTRESS.md:118–145` is stronger than these results. **Fix:** carry expectation provenance and coverage (including missing edges) in *every* outcome; require full coverage for every pin issuer and pin consumer. Do not aggregate partials as matches or use “missing seal headers” policy as permission to ignore missing objects.

3. **A two-stage, post-commit writer conflicts with the new strict branch policy and cannot guarantee operation identity.** Prepared now checks **local heads**, too (`src/hooks.rs:614–624,632–653`). On an ordinary new unsealed commit to an attached branch with `buttress.missing=error`, the first branch update can be rejected **before** the hook that would seal it can run. This is not simply strict rejection of a remote plain branch: it prevents the advertised local producer from producing compliant commits. Git updates HEAD before invoking `post-commit` (`builtin/commit.c:1945–1972`); under permissive policy the intermediate ID is actually published. The early and late `(symbolic-ref, OID)` reads are an improvement, but neither is an atomic assertion on the final transaction: it updates one direct ref against an old **OID**, with no condition on HEAD's symbolic state (`src/hooks.rs:217–251,404–450`). A checkout in the remaining interval can leave the updated branch no longer current; no-deref plus an old OID isn't a “must still be detached” predicate (Git `refs/files-backend.c:2764–2792`). Even the already-sealed fast return doesn't recheck HEAD. The wrapper observes a before/after OID and reads the *entire* `logs/HEAD`, then seals a fresh lookup, not an ID certified to come from this commit invocation (`src/hooks.rs:958–985,1012–1049`). **Fix:** construct/verify/sign the final object before publishing it in an update bound to the intended ref, old value and worktree state. Do not solve the ordering problem by generally exempting branch updates.

4. **Signature and release issuance do not establish full intended history or signer.** Existing sealed HEAD's own tree and immediate parent digests are checked; direct conflicts fail and `--sign` now rewrites a valid unsigned seal. But `digest_commit` on a sealed parent hashes the parent's *claim bytes*. The writer discards the returned frontiers and never verifies the reachable claims before signing (`src/hooks.rs:280–317,324–342,363–390`; `src/protocol.rs:566–584`). Presence of `gpgsig*` suffices to call a seal signed or request re-signing. No old/new signer or signature validity is checked. Stock `commit -S<key>` is not an instruction carried into `sign_payload`, which independently reads `user.signingkey` (`src/hooks.rs:86–99,146–152,275,307,1033–1036`). A different valid local signature is not the one requested. Unsigned sealing still uses unverified SHA-1-indexed cache hits *as the published header values*, not just as bookkeeping (`:319–342`; `src/protocol.rs:459–483,566–575`). Fresh re-read of the **new commit** is good, not revalidation of its children. Autotag's create-only direct update largely fixes destructive overwrites, not failure of the original and companion refs to publish together; committed-hook status cannot veto the first update (`src/hooks.rs:694–717,745–781`; `githooks(5)`, “reference-transaction”). **Fix:** use a fresh full verifier on a stable view for every attestation; preserve explicit signer choice, verify required signer identity, and use explicit transactional release issuance with immutable direct companions. Keep historical pins/retention a separate policy.

5. **Installing forwarding stubs changes Git semantics even when there was no prior hook.** This is not just a failure to forward a name. For `receive.denyCurrentBranch=updateInstead`, Git invokes its built-in worktree/index checks and update **only if no `push-to-checkout` hook was invoked** (Git `builtin/receive-pack.c:1433–1472`, `githooks(5)`, “push-to-checkout”). The always-executable stub exits 0 even with no delegate (`src/hooks.rs:1289–1317,1379–1411,1645–1678`). Git can then advance the branch without the normal checkout. An inert `proc-receive` is likewise not an implementation of the pkt-line protocol if that hook is configured for use. Also, local enable reads only `--local` state; it can mask a previously effective global/system hook path. With a configured prior path, the stubs fall back to default hooks when a particular hook isn't executable there; stock Git uses the configured directory **instead of** the default. This can unexpectedly activate hooks the user had turned off (`:1341–1364,1596–1609,1622–1636,1656–1671,1690–1712`). **Fix:** integrate only the two needed events (native additional hooks on supported Git versions are worth considering). Preserve both the previously effective lookup and the *absence* of other hooks. Manifest ownership, validate scope, stage the install and roll back on failure.

6. **Git's command context and the Rust-side filesystem context diverge.** Git subprocesses replay the global argv, but discovery joins relative `rev-parse` paths to the *original* cwd, ignoring the effective `-C` directory (`src/git.rs:240–258,265–289,315–322`). **Observed** on a valid repository: both returned Git paths from stock `git -C fixture rev-parse` were `.git`; Rust resolved `git_dir()` to the wrong directory. Rust-side reflog reads, shallow boundaries and the unsigned writer cache can then concern a different repository, even though `cat-file` and `update-ref` run in the intended one (`src/hooks.rs:310–322,458–461,958–961`; `src/git.rs:671–694`). No unusual ref syntax or changing repository is needed. **Fix:** request absolute effective paths from Git, frame each byte path unambiguously, and use Git's effective shallow path/override. Test multiple `-C`s, linked worktrees and redirection of git-dir/common-dir.

7. **Unbounded work remains on a path holding ref locks.** Normal blobs reached from directory entries stream in 64 KiB chunks. Direct `verify_target` still first requests all bytes of the start object (`src/protocol.rs:932–938`); `read_object_inner` exempts blobs from the 64 MiB cap, then allocates `size` bytes (`src/git.rs:529–548`). Type-mismatched metadata links can also arrive as full blobs. Tagged blobs can be streamed twice (`src/protocol.rs:966–984,1016–1019`); direct `id` also reads the whole blob before hashing (`src/main.rs:204–208,259–264`). The instrumented small-blob test confirms the double API path without a stress test. No aggregate limit on expanded bytes, refs, records, visited objects, edges, or time. Memoizing a frontier **vector per plain commit** can take quadratic space/work across a wide frontier shared by many descendants (`src/protocol.rs:641–662`); `verified_seals` saves comparisons, not the repeated BFS of parent edges for each ref (`:1095–1164`). The whole transaction/reflog/listing is buffered (`src/hooks.rs:477–508,958–961,1195–1211`). **Fix:** obtain bounded type/size metadata first, stream a blob once, share completed *transitive* verification state parameterized by coverage, and enforce per-operation budgets with an explicit error. The kernel timings in `BUTTRESS.md:215–244` aren't bounds on this implementation.

### Medium

* **The public verification API has weaker preconditions than its result needs.** Built-in callers use fresh memory caches, but exported `verify_target_with_engine` accepts an `Engine` built with any cache; its purported cache check does nothing. Public keys are replaceable at construction, and `put_commit_cache` accepts arbitrary values (`src/protocol.rs:19–34,403–436,566–575,903–916`). `&mut S` excludes another Rust borrow, not another process changing a repository; `ObjectStore` doesn't guarantee consistency across `has_object`, `hash_blob` and `read_object` (`src/git.rs:194–206`). On error, earlier digests/frontiers and locally checked seals remain cached. Reusing these is sound only with canonical keys, trusted memo entries, and the same stable snapshot. Use a verification-only constructor/type that cannot load/inject writer hints; specify and enforce snapshot lifetime. This is **not** a disk read by built-in `check`.
* **Revision spelling still determines evidence.** `check` resolves the user's expression first, then passes that spelling, not the validated ref chain, as a hint (`src/main.rs:310–320`). Stock pre-peeling can remove a trailer-bearing tag before Rust sees it; `HEAD`/symrefs can conceal the pinned ref name. Conversely a marker in a revision's path or other non-ref text isn't a ref pin. The parser now rejects several walk operators *after the marker*, but this is not Git's revision grammar (`src/protocol.rs:672–698`). The exact-pair policy still exempts **errors**, not just warnings, under strict policy and takes the base before the first marker, not necessarily a single terminal suffix (`src/hooks.rs:563–578,632–653,1218–1229,1253–1271`; compare `CONTRACTS.md:337–343`). Verify actual direct ref names and attached tag bytes, handle derived objects as explicitly separate requests, and apply a documented policy per ref.
* **Object validity and signature framing aren't Git-equivalent.** Fixed prefix ordering prevents choosing a different target from Git on a jointly accepted tag; acceptance is another matter. Header-only input need not have a terminal LF in Rust. Git requires LF after the tag name (`tag.c:185–197`); `fsck_tag_standalone` checks refname/identity and reads an optional signature header in order (`fsck.c:1068–1125`). Rust checks a nonempty name, accepts repeated signature headers or a tagger after one, and doesn't check tagger identity (`src/protocol.rs:127–135,733–764`). Conversely Git can peel a tag with extra headers that Rust rejects. Trailer scanning covers **all body lines**, not just a Git trailer paragraph; the terminal armor helper checks an end *suffix*, not a full end line, accepts a bare CR after a begin marker, and doesn't validate armor contents (`:766–856`). Stock `parse_signed_buffer` selects the **last recognized line start**, not the same begin/end test (`gpg-interface.c:702–728`). Define a precise accepted subset; don't equate delimiters with a verified signature. For commits/trees see M8 below.
* **Transaction and store errors are still incompletely typed.** Exact LF consumption and propagation of stdin I/O errors are improvements, but the old token is unchecked; the parser accepts additional spaces as ref bytes and doesn't validate the grammar of a `ref:` target. The internal seal token binds only old/new, not the ref; autotag's token omits old/type. Discovery exempts errors via substring matches on diagnostic text, not typed states (`src/hooks.rs:477–552,584–620`). Stock Git is a trusted producer of ordinary records; a malformed record is not proof a remote can control hook stdin. `StoreFailure` correctly distinguishes returned I/O errors, **not** the cause of every Git `missing` response: `cat-file` can report `missing` for a negative object-info lookup (`builtin/cat-file.c:544–557`); child stderr is discarded (`src/git.rs:415–459`). Absence also doesn't prove promisor status. Default prepared tolerates general `Incomplete`. Use typed discovery/records, exact exemptions, and require positive authorization for incomplete verification.
* **Wrapper policy and failure propagation are conditional.** Parsing raw OS arguments and propagating attempted fallback failure are fixes. Quiet delegates entirely, so an ignored post-commit failure is still not detected; independent scanning of all commit argv for `-n`/`--no-verify` conflates option values/pathspecs with switches. Stock `--no-verify` does not disable post-commit. The wrapper injects `-q` and fabricates a partial summary rather than preserving Git output. The pre-open can fail silently, and changed OID/log bytes don't identify the creator. Promotion of manually parsed `-c` values over Git's effective config can defeat later `--config-env`/Git boolean semantics. On a SHA-256 repository an otherwise successful normal stock commit can be followed by reopen failure/exit 1; wrapped fsck instead skips this format (`src/hooks.rs:824–891,894–955,973–1049,1052–1159`). Wrapped fsck audits *all enumerated refs*, not necessarily the explicit object roots supplied to stock `fsck`. Preserve full Git semantics or make these operations explicit commands; distinguish “commit exists; sealing failed” from a failed commit.
* **Installation and cache persistence overstate I/O guarantees.** Per-file exclusive temp + rename is not atomic installation; rename can *replace* a destination hook symlink/unowned file (it does not truncate its referent). Disable unlinks hook names without ownership checks; config unset, local disable, chmod and cleanup errors can be ignored. Missing state on repeat can lose prior settings; the subcommand symlink and custom-bin-dir ownership aren't tracked (`src/hooks.rs:1351–1365,1413–1474,1508–1569,1729–1761`). Cache load does `symlink_metadata` then ordinary `open/read_to_end`. Flush uses one handle but no lock or append arbitration, clears pending on failures and may truncate on validation I/O error. Its output can cross the load cap, after which even a successful flush doesn't round-trip. `O_NOFOLLOW` fallback is zero on other Unixes (`src/cache.rs:75–114,165–247`). Use handle-based validation/limits, platform flags, locking or atomic replacement, and surface write/restore failures; do not promise exact persistence for best-effort caches.

### Low / Informational

* **Low:** `plain_covered` counts *all* plain commits in the shared engine, not reachability from this target (`src/protocol.rs:1174–1183`); a per-ref result can include earlier targets' work. Reflog subjects are bounded/filtered, but not all tag names, Git errors, or human-facing strings pass through the display sanitizer (`src/hooks.rs:391–402,627–630,737–779,787–791`; `src/main.rs:61–69,478–486`). Escape at the presentation boundary, not in stored bytes.
* **Informational:** Same digest is computational binding to the **specified input**, not tag authentication, a transitive submodule check, or proof that a remote selected the intended branch. §7 now correctly conditions history binding on every reachable comparison (`BUTTRESS.md:170–206`). There is no stored authenticated last-seen-ref continuity policy; `[sig]` denotes a header. “Every hash call uses `hash_with`” in TB-4 is now literally false: incremental `Hasher::new/update/finalize` is used too. The locked build still doesn't enable `zeroize` or use `throughput::update_each`; the specific round-1 wiped-hasher advisory rationale is not a new hash break (`Cargo.toml:13–14`, `Cargo.lock:12–38`, `src/git.rs:600–625`, `features.txt`).

## Design-by-contract ledger

“Conditional” below is an actual restriction on an `ensures`, **not** an additional guarantee supplied by Rust's type system. `CONTRACTS.md:9–12` makes undocumented preconditions relevant. Related private helpers are grouped with their callers. Some functions have no individual contract at all, despite the claim in `src/lib.rs:3–14`.

## Acceptance recommendation

For a release today, validate stock Git object **and ref** integrity, use a stable complete repository, check the exact unpeeled canonical ref/object with `--expect <independently authenticated digest> --no-shallow`, require a full match, and ensure the consumer uses the same resolved target and replacement policy. Verify any required signature and authorized signer separately. This is a narrower, defensible use than treating default hook or fsck success as provenance.

Before making automation a gate: (1) make ref inventory, expectation source and complete coverage explicit at every caller; (2) unify final-object signing, validation and publication; (3) preserve Git's effective path/config and absent-hook semantics; (4) isolate trusted verification state and bound work. Keep the ordinary `-C` and direct-blob contract assertions, canonical differential vectors, and binary hook replay in CI. Add acceptance coverage for strict **local production**, inherited hooks paths, ref-database errors, trailer-only shallow checks and per-target coverage on a warm engine. These exercise the boundaries at which correct individual digest calculations still produce an incorrect system result.
