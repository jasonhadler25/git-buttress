# Independent security and contract audit: `git-buttress`

**Revision:** `67a64570760bf3019232af13a3c706539086a0d1` · **Disposition:** do not use the automatic hook, wrapped `git fsck`, or `MATCH` alone as a release-acceptance gate.

## Executive decision

The main problem is **what was checked**, not BLAKE3. On a stable, complete store of canonical Git objects, the four digest encodings implement a sensible, domain-separated commitment to the specified content. The release tests passed, and independent comparisons with `b3sum` agreed. But the program can check a different target from the one Git uses, omit evidence it already knows exists, or exit successfully without checking a ref transaction at all. A stronger hash does not fix any of these outcomes.

| Priority | Finding | Why it matters |
|---|---|---|
| Critical | C1. Git and buttress can peel the same annotated tag differently | Even an independently trusted BLAKE3 pin can be matched against the wrong object. |
| High | H1–H4. Lost hook records, skipped sealed ancestors, false-clean ref enumeration, partial verification reported as success | The common automation paths are not fail-closed. |
| High | H5–H7. Sealing the wrong HEAD, replacing contrary evidence, trusting a SHA-1-indexed writer cache | A local operation can publish the wrong commit, digest, or signature. |
| High | H8–H11. Wrapper context/flag loss, nonatomic companion tags, destructive hook installation, unbounded verification work | These affect ordinary users as well as adversarial repositories. |

**Immediate mitigation:** For a release, obtain the *intended target's* digest through an authenticated independent channel. Use a complete, isolated, non-changing repository, enforce stock Git object-format checks, reject ambiguous tag structures, and check the exact canonical target with `git buttress check <target> --expect <trusted-digest> --no-shallow`. Verify any required signature and signer identity separately. Ensure subsequent materialization uses that same target and object view, including the replacement-object policy. Do not treat success of `id`, a post-commit hook, `--missing silent`, or a remote-supplied trailer as equivalent. This is defense in depth, not a workaround for arbitrary untrusted Git installations or concurrent object replacement.

## 1. Exactly what the digest commits to

* **Files and domains.** `src/protocol.rs:29–73` derives four context keys from the four exact spec strings, uses `DeriveKeyWith` and returns 32 bytes. For fixed proper contexts, changing a file's bytes or confusing a file with a directory requires finding a collision in the domain-separated construction. This is **computational binding**, not mathematical injectivity of a finite-length function. The keys are public, not authentication keys.
* **Trees.** `src/protocol.rs:324–360,472–513`: mode is carried as the original octal bytes, then space, raw name, NUL, then a field whose width is determined by that mode. The decoder can find the next entry unambiguously. No text normalization, sorting, executable-bit stripping or symlink following. A regular file and symlink with the same blob have the same *blob* digest, different *tree* inputs. Changing the spelling of the mode, name, order, symlink target bytes or gitlink **pointer** changes the tree input. Recursing gives binding to the unfolded hierarchy on acyclic graphs. A gitlink's target repository contents can change under the same 20-byte pointer without changing this digest (`BUTTRESS.md:75–83,200–201`). This is a real limitation under the proposed SHA-1 threat model.
* **Content identity is not storage identity.** Normal non-gitlink child SHA-1s are *replaced*, not included alongside the BLAKE3 values. In the arbitrary-OID map of `CONTRACTS.md:33–50`, different raw trees can name different OID aliases for identical child content and have the same directory digest. Identical expanded content does not certify object sharing, pack representation, unreachable objects or the ref database. This is not a distinct-content collision. In ordinary correctly named Git storage the same typed bytes deterministically get the same Git OID.
* **Commits.** `src/protocol.rs:539–550,583–596`: plain/stale = directory digest, checked `u32` parent count in little-endian, ordered fixed-width parent digests, then *all* raw commit bytes. Even a message-only change alters the input. Sealed = *only* raw commit bytes; it commits to the **claims** in those bytes. The claimed and actual histories are bound together only after every reachable comparison succeeds. Holding a sealed commit fixed while the store beneath it changes leaves `id` unchanged; a plain descendant whose digest walk stops there can likewise retain its digest. A complete verifier with a trusted root detects the substitution. It is not a BLAKE3 second preimage. Thus the unqualified conclusion of `BUTTRESS.md:170–189` is too strong. Tags are peeled, not a fifth hash domain: tag message, tagger, signature and intermediate tag identities are not authenticated by a target digest.
* **Trust.** An unpinned sealed root can be internally consistent but not the intended release. Its own message, author, committer, etc. are not checked against any earlier value just because its child links check out. A digest in a tag *chosen by the same remote*, or an unsigned trailer, is not intrinsically independent evidence. No code verifies signature trust or persists/compares an authenticated last-seen branch digest during fetch (`src/hooks.rs:364–405`; `src/protocol.rs:731–769,844–864`). Already possessing an old commit is not a continuity/anti-rollback policy. A `Match` is not a provenance verdict. `README.md:109–138,215–219` partly states this boundary but gives too much weight to having a prior clone or a signature present.

**Answer on interoperability: no, not on every input.** The valid encodings tested agree with `BUTTRESS.md:56–99`. See M1 for byte/parser divergences from Python and H2/H4 for conflicting reader semantics in the two specifications. No change of cryptographic primitive is needed to fix those defects.

## 2. Ranked findings

### Critical

**C1 — A pinned annotated tag need not designate the object Git will use.** `src/protocol.rs:638–653,752–794`; `src/hooks.rs:405–407`; `src/main.rs:190–201`. Static, cross-checked against upstream [Git v2.56.1 `tag.c`, lines 130–203](https://github.com/git/git/blob/v2.56.1/tag.c#L130-L203). Git takes the leading object and type in fixed order, requires a tag name, and binds its parsed target there. Buttress scans the whole header, with *last assignment winning* for both fields; it does not require canonical ordering or even a tag name. Checking the declared kind of **its selected object** is insufficient. Where a malformed but Git-peelable tag reaches the verifier, a green pin check can describe one commit and subsequent stock Git peeling another. Neither hash has to be broken. Critical for the advertised dependency-pin use case; does not apply to a canonical unambiguous tag, and independent strict rejection at ingestion reduces exposure. **Fix:** use one shared byte-level parser consistent with Git, reject ambiguity, duplicates and invalid structural ordering before accepting any expectation, and bind consumption to the validated target. Require agreement with Git's target on the entire accepted tag language. Reuse it for `check`, `id` and autotag; test parser equivalence, not just syntax errors and target kinds.

### High

**H1 — Prepared hook can succeed after reading only part of a transaction.** `src/hooks.rs:332–354,378–397`; cf. `CONTRACTS.md:326–336`. `.lines()` requires UTF-8; `.map_while(Result::ok)` silently ends at a decode **or I/O error**. Git ref names on Unix are bytes, not necessarily UTF-8. `filter_map` drops incomplete records; `split_whitespace` uses Unicode whitespace, not the protocol's two ASCII spaces; extra fields and bad new OIDs can be ignored. Thus even later, otherwise perfectly valid updates may never reach `verify_target`. Separately, **any** `GitRepo::open` error is treated as outside the supported repo. This is hook exit 0 without a check, not a forged BLAKE3 `Match`. `GIT_BUTTRESS_INTERNAL` is also an unconditional, inherited opt-out, not an authenticated indication of which update is internal. **Fix:** parse bounded LF-terminated byte records with exact ASCII framing, validate every field, preserve opaque ref bytes, and propagate input and discovery errors. Distinguish positively identified unsupported environments from failures inside a supported repo. Scope internal exemptions to the exact operation.

**H2 — An unpinned plain/stale tip hides contradictory evidence in sealed history.** `src/protocol.rs:543–550,844–875,880–898`; `BUTTRESS.md:118–142` vs. `CONTRACTS.md:285–291`. The plain digest walk finds sealed boundary commits and hashes their *headers*, not their contents. `verify_target` returns `NoEvidence` before using that boundary list if the root itself is not sealed and has no expectation. A bad directory/parent claim in a reachable sealed ancestor then gets no comparison. Default `check`, `fsck`, and prepared hook can succeed on that history. `--missing error` can reject it for the *wrong reason*. This obeys the literal early-return contract but contradicts the wire specification's walk and the promise that mismatch is always an error. **Fix:** decide root evidence status **after** checking all reachable seals, with mismatch taking precedence. Lack of a root anchor and the presence of contradictory ancestor evidence are separate facts. Include mixed histories in which the *starting* commit is plain/stale, not just sealed tips covering plain ancestors.

**H3 — `buttress fsck` treats ref-enumeration failure as a clean empty repository.** `src/hooks.rs:926–939,985`; `src/main.rs:335–340`. Every error from `git show-ref`, including a broken ref, read error or failed child, becomes `Vec::new()`. Previously emitted rows are also lost on a nonzero status. Success with `0 ref(s) verified` is possible even under strict policy. Successful listings are parsed lossily and tokenized with Unicode whitespace; a valid name/pin can be truncated. `show-ref` without `--head` also omits a detached HEAD not reachable from another ref. The wrapper first runs stock fsck (`src/hooks.rs:859–885`), which catches some repository errors; that doesn't repair standalone `buttress fsck`, and stock fsck doesn't check BLAKE3. **Fix:** use exhaustive byte-preserving ref iteration with an unambiguous empty-success case, reject malformed output/errors, include detached HEAD and specify the scope (not reflogs/dangling objects). Never translate discovery failure to verified success.

**H4 — Incomplete coverage can be counted as a full match, even for a pin.** `src/git.rs:223,417–428`; `src/protocol.rs:901–921,950–956`; `src/main.rs:228,267–287`; `src/hooks.rs:405–408,435–445,951–955`. An absent parent of a sealed commit listed in the shallow set is skipped with `allow_shallow`. `check` defaults to allowing this and prints `MATCH`/0 plus an incomplete count; the hook and fsck hardcode `true` and discard the count. Neither an explicit pin nor `missing=error` makes that edge get checked. An adversary controlling the boundary and object availability controls how much history is *examined*, not the BLAKE3 digest of bytes actually checked. A marked commit with a **present** parent still gets checked; plain history cut by a missing parent is `Incomplete`. The library behavior is actually specified/tested (`CONTRACTS.md:293–298`; `tests/integration.rs:621–647`), but the callers' unqualified success conflicts with `BUTTRESS.md:141–142`. The boundary is a one-time read of `common_dir/shallow`, ignores read/parse failures, and isn't necessarily Git's effective temporary/alternate shallow file.

There is a second, different issue: all object-store errors map to `Incomplete` (e.g. `src/protocol.rs:387–391,408–412,455–461`); prepared tolerates this for unpinned refs under silent/warn. Corrupt packs, Git/batch failures and genuinely promised-but-unavailable objects aren't distinguished. A first missing object can stop traversal before independent contradictions are examined. A later lazy object arrival/checkout is **not** rechecked by a blob-read hook; none is installed (`src/hooks.rs:1022–1037`). `README.md:127–131` does not hold. **Fix:** model full, prefix-only, promised-missing, corrupt-store and operational-failure states explicitly. Fail closed for strict/pinned workflows, expose precise boundary OIDs and coverage on every caller, and verify after materialization before use. Only permit partial success under an explicit policy about partial history, not a policy about *absence of seal headers*.

**H5 — HEAD CAS checks an OID, not the identity of the commit operation or its branch.** `src/hooks.rs:176–184,269–308,769–801,805–840`. `HEAD`'s OID is read first, its symbolic target only **after** hashing/signing. A checkout to another branch at the same OID can cause the wrong branch to be updated; a later checkout can make a successful update no longer be the current HEAD. Symbolic-ref errors are all interpreted as detached; lossy UTF-8 conversion and `trim()` can change a valid ref name. In detached mode `--no-deref` is helpful but does not atomically establish that HEAD *remained detached*. Ordinary changed-OID races on a fixed direct branch do fail the CAS. Under the assumed SHA-1 break, equality of that OID is also not a byte-identity CAS. The wrapper independently rereads HEAD after Git exits; it doesn't know that the commit it seals/prints was the one just created. A plain/intermediate ref is published before the post-hook rewrite; observers, other hooks, and reflogs can see it. This refutes `README.md:203–210`. **Fix:** construct and sign the final object before publishing, or capture the exact intended ref+OID at creation and verify its symbolic/direct state and old value in one ref transaction. Do not downgrade lookup errors to detached mode; report the exact returned commit, not another lookup of HEAD. Abort on ambiguity; don't race to rewrite someone else's commit.

**H6 — Sealing can replace evidence of tampering and change who signed it.** `src/hooks.rs:192–230,232–269`; `src/protocol.rs:964–983`. A syntactically current seal whose digest comparison **fails** falls through to the same rewrite path as a new plain commit. It removes the old evidence and signature, constructs claims for the current store and may sign them with the local key. That's different from the protocol's benign *stale tree-ID* case. Also a valid seal returns at line 216 **before** `force_sign` is considered: `seal-head --sign` can succeed on an unsigned, already sealed HEAD without signing. Presence of a `gpgsig` header, not its validity or signer, requests re-signing. An explicit key selected for stock `git commit -S<key>` is not carried into this operation; `sign_payload` rereads `user.signingkey` (`src/hooks.rs:63–74,117–126`). An original signer, or the same committer's intentionally different key, need not be preserved. **Fix:** reject contrary current evidence, require explicit consent for repair/re-attestation, check signer intent/identity, and make `--sign` a real postcondition. Integrate with the original signing operation rather than replacing a signature after the fact. The idempotence clause in `CONTRACTS.md:318–322` needs a signing exception.

**H7 — The unauthenticated writer cache is an input to signatures and release pins, not a hint.** `src/hooks.rs:182–187,197–228,249–270,504–529`; `src/protocol.rs:404–407,433–435,526–534`; `src/cache.rs:93–124`. A cache hit skips recomputation. No proof binds cached values to current bytes, repository snapshot, or context strings. Even a cache produced honestly can be stale under the stipulated SHA-1 substitution model; an edited cache needn't even describe objects in this repository. Sealed parent digests are just hashes of the raw parent claim, not confirmation of its descendants. The resulting signature/pin can attest a different view, fail on a clean reader, or bless claims the writer never checked. After `hash-object -w`, the code hashes `final_raw`, not a fresh read of the object Git will actually serve under `new_oid` (`src/git.rs:342–345`; `src/hooks.rs:269–270,308–310`). Object reuse at a colliding name isn't ruled out by CAS. **Not** a disk-cache read on `check`: TB-1 holds in the application's reader. **Fix:** use a fresh verification engine over a stable object view for signing and pin issuance, including ancestral seal validation; re-read stored bytes before publication. Invalidate/version any performance cache and never use a SHA-1-only cache hit as proof. Protect the object store for the duration of verification and subsequent use.

**H8 — The transparent wrapper can mutate after a preview, ignore failed sealing, or verify with the wrong settings.** `src/hooks.rs:556–576,583–647,650–714,717–752,763–802,852–891`. Three separate postconditions fail:

1. Success from `git commit` is treated as evidence that a commit was created. Preview detection is a partial flag parser. For instance Git's `--null` synonym of `-z` is absent, as are some combined/abbreviated forms. Stock Git can exit successfully from a status-only operation and the wrapper then seal the *previous* HEAD and append human-readable output. Short options with attached arguments are scanned as letters or skip the next token based on the **last** character. Conversely quiet and `--no-verify` bypass wrapper fallback; `--no-verify` is not a preview and does not disable stock post-commit. See Git v2.56.1 `builtin/commit.c:1258–1267,1422–1423,1749–1764,1836–1837`.
2. A post-commit hook cannot veto the original commit. The wrapper explicitly drops the `Result` from its fallback seal (`:798`) and returns 0 even if signing, CAS, or repository discovery failed. It can print a success summary for an unsealed commit. That doesn't mean Git created no commit on error; retrying blindly is unsafe.
3. Git's global argv is not replayed for post-actions. Only a subset of `-C`/`--git-dir` is reconstructed; opening a cwd at a git-dir path isn't equivalent to setting `--git-dir` (including gitfiles). Work-tree, namespace, config-env, and ordinary `-c` settings such as the missing policy are skipped or not applied; only `buttress.disabled` gets special treatment. Wrapped fsck returns 0 on failed reopen. Literal subcommand matching is not alias or library interception. `src/main.rs:28–30` also makes the *entire* wrapper panic on a non-UTF-8 argument, including a path passed to an otherwise unrelated Git command.

**Fix:** keep `OsString` arguments and original Git execution context. Prefer an explicit operation or a Git integration that observes an actual commit/verified transaction, not a reimplementation of Git's option parser. Never infer a new commit from exit 0; propagate post-action failures with a diagnostic distinguishing “commit exists, sealing failed.” Make wrapped fsck say whether/where buttress actually ran.

**H9 — Autotag can overwrite another ref and cannot guarantee its advertised update.** `src/hooks.rs:456–470,487–537`. The committed-phase hook peels independently, discards declared kinds/trailer expectations, uses the writer cache and issues unconditional `update-ref` without an expected old value or `--no-deref`. An existing companion (including a symbolic ref) or concurrent update can thus redirect/lose an unrelated ref value. Even without a race, two different annotated tag objects can have the **same peeled digest**. Checking the old target separately is not CAS. The original tag is already committed; companion failures are swallowed, and a missing object can return `Ok` for the *whole* batch. Old digest-suffixed names remain after retarget/deletion. `GIT_REFLOG_ACTION` and the presence of remote-tracking refs are heuristics, not proof of local user intent (e.g. tag-only transactions, server-side receive). Git ignores a `committed` hook's exit status. **Fix:** make release-tag issuance explicit, validate the peeled target with one shared verifier, and create both direct refs in one atomic transaction. Treat pin names as immutable/create-only, verify an existing identical association without dereferencing symrefs, and report conflicts. Define retention of old pins separately.

**H10 — Enable/disable can disable unrelated security hooks or destroy user files.** `src/hooks.rs:999–1010,1022–1057,1066–1088,1098–1119,1151–1195`. Replacing `core.hooksPath` affects **all** hook names. Only two are chained, and only when a prior *configured* path is found; default `.git/hooks` and other hooks such as pre-commit/pre-push/receive hooks disappear from dispatch. Repeat enable forgets the prior path. Disable unsets a potentially unrelated setting without checking ownership/restoring it, ignores errors, and leaves scripts/subcommand symlink. A global wrapper can still seal even after a local disable. Subcommand installation unlinks an existing `git-buttress` entry and ignores symlink errors. Script writes truncate and chmod existing paths, follow symlinks, and are not transactional; even a dangling `git` symlink can get past `exists()`. Path aliasing can defeat lexical “same file” tests. An error after the config change leaves a partial installation. **Observed:** see `lifecycle.log`. **Fix:** refuse conflicting installs by default; preserve prior config/scope and all hook behavior (including defaults); use a manifest, ownership/identity checks, exclusive creation/atomic replacement and rollback. Disable should restore only what this install changed and surface errors. Don't install system-wide in a security-sensitive environment before this is addressed.

**H11 — Untrusted object sizes and ref multiplicity have no resource budget.** `src/git.rs:380–409`; `src/protocol.rs:210–216,383–401,472–496,543–594,746–801`; `src/hooks.rs:332–344,405,927–952`; `src/cache.rs:44–63,98–106`. Batch size goes straight into `vec![0; size]`; whole expanded blobs/commits, entry vectors, raw trees on the traversal stack and repeated commit clones consume memory. Top-level objects can be read twice, and parent existence probes read whole objects. There are no length/work/time limits. `fsck` starts a fresh traversal **per ref**, even for many aliases of the same tip, and the hook repeats per distinct tip/pin while Git holds ref locks. The deterministic map hasher depends on just the leading eight OID bytes for an OID-sized write; the “uniform OID” assumption fails in the advertised arbitrary-OID model. Hash flooding harms availability, not key equality. Small on-disk packs need not mean small verification work. Possible OOM/abort, excessive CPU, stalls, and rejected or blocked ref transactions. **Fix:** stream blob hashing with checked object/frame sizes; bound aggregate expanded bytes, objects, edges, refs and time; use keyed hashing and share verified subgraph results within a snapshot while checking each expectation separately. Treat budget exhaustion as explicit verification failure. `BUTTRESS.md:212–235` benchmarks a different program/backend, not this verifier's worst case.

### Medium

**M1 — Python is a vector generator, not a normative parser.** `buttress-vectors.py:9–16,22–56,58–74`; `src/protocol.rs:139–171,183–304,324–360`. It takes the first tree header, recognizes only literal current-line prefixes, checks a repeated tree ID and counts parent lines via an `assert` (disabled with optimized Python); it doesn't validate the claimed hex digests. Duplicate tree evidence or orphan parent evidence can fall back to plain instead of mismatch. Splitting an initially empty header block also differs. The tree reader accepts a broader octal grammar/length, doesn't enforce name restrictions or a full child width (notably for gitlinks), and typed `git cat-file <type>` can perform conversions/peeling where Rust requires the stored kind. No SHA-1 format check, no replacement/lazy-fetch isolation, no active-path cycle detection; recursive calls can exhaust resources before `functools.cache` has a result. `buf +=` entails repeated copying on wide trees. Missing objects generally raise subprocess/parse exceptions rather than a classified error. Its example “new commit” appends lines even when already sealed and doesn't remove/re-sign an old signature. The read-only claim does not prevent Git itself fetching missing objects. **Fix:** explicitly restrict the utility to canonical, complete, acyclic SHA-1 fixtures or implement the same grammar, validation, object view and error cases. Add differential accept/reject tests as well as positive vectors. `BUTTRESS.md:33–34,70–83,101–114` should explicitly state the accepted algorithm-token grammar, mode/name restrictions and stale-vs-malformed precedence.

**M2 — Verification scope is narrower than fetch/checkout/fsck claims.** `src/hooks.rs:378–405,556–576,921–939`; `src/git.rs:235–241`; `README.md:125–144,175–177,203–214`. Prepared examines certain **destination names**, not “incoming objects”: ordinary `refs/heads/*` updates in mirrors/bare servers, custom refspec destinations, FETCH_HEAD-only flows, symbolic updates and deletions can be outside policy. Library clients such as libgit2 are not guaranteed to invoke CLI hooks/wrapper. Full stock fsck and buttress fsck are different functions; the latter does not visit every stored object. Verifier subprocesses intentionally ignore `refs/replace`; ordinary Git invocations/checkout can honor them, so a check of raw storage is not a check of the replacement view. Local grafts/shallow/revision metadata may also affect what revision Git resolves; they do not rewrite the parent bytes the Rust parser reads. **Fix:** specify supported transactions/clients, protect configured namespaces (including pinned symrefs), and reject or consistently disable replacement/graft views for downstream use. Verify a trusted manifest/target independently of where a refspec stores it. Do not promise checkout interception.

**M3 — Pin and missing-policy semantics depend on aliases and how the caller spelled the revision.** `src/hooks.rs:364–375,399–425,945–975`; `src/protocol.rs:616–634`; `src/main.rs:233–245,256–267`. The “suppress warning for a plain companion tag” exception suppresses **errors** too, for *any* ref with the same OID as *any* name containing a valid pin, not necessarily its matching tag pair. Hook deduplication is by OID, not policy result. `fsck --missing error` can count no-evidence refs and return success despite `CONTRACTS.md:335–336,353–354`. Valid pins themselves are still compared if parsed and processed. In `check`, expectations come from the user's revision string, not necessarily the resolved ref. Git pre-peeling can discard an annotated trailer before the validator sees it; `HEAD` can hide the actual branch name. Conversely `^`/`~` token splitting can apply a base ref's digest to a different, derived target. Multiple `--expect` arguments silently replace one another. **Fix:** separate raw ref identification/peeling from revision expressions, attach expectations to the correct object, reject ambiguous/conflicting arguments, and enforce policy per protected ref. If alias evidence is intended, specify exactly the relationship and never silently weaken strict policy.

**M4 — Tag trailer framing is not “strip a trailing signature block.”** `src/protocol.rs:655–694`; `CONTRACTS.md:252–259`. Unanchored substring search truncates at a marker anywhere in body text, even ordinary prose, without requiring a complete block at the end. It tries PGP before SSH rather than following actual block order. Legitimate trailers can vanish; unrelated message lines can count as trailers, including text that is not in a real trailer block. A reserved trailer key without the exact prefix/space can be ignored; `.trim()` also accepts additional whitespace. Unsigned trailer and unauthenticated name mustn't be called trusted just because their strings agree. For nested tags the trailer OID binds the **immediate** target, but its digest is ultimately compared to the **final peeled** target; define that explicitly or disallow tag-to-tag trailer claims. **Fix:** parse bytes using Git-compatible terminal signature framing, define one precise trailer grammar and reject malformed/ambiguous reserved fields. Check signatures with an explicit trust policy when authenticity is required.

**M5 — `GitRepo` and subprocess discovery rely on stronger assumptions than the contracts.** `src/git.rs:66–102,158–164,190–241,274–316,380–402`; `CONTRACTS.md:96–104,176–204`. The discovery `rev-parse` has `--no-replace-objects` but **not** both promised environment settings; a missing format output becomes `"sha1"`. Lossy, newline-delimited path parsing is not faithful for all Unix paths. `cmd`/batch **do** set both variables. Git discovery tests file existence, not executability, identity or trust; explicit or relative PATH entries need not resolve to the same program in a changed cwd. Wrapper detection requires a successful read and valid UTF-8 of the *entire* prefix; it isn't a byte substring test and fails open on open/read errors. A different forwarding wrapper also need not carry the marker. Symlinks, path changes or chained hooks using equivalent-but-not-identical directory paths can re-enter wrappers/hooks; no recursion-depth guard. A generated ordinary ASCII wrapper on stable absolute PATH is recognized, as the existing test shows.

Batch framing resets `batch=None` on returned errors and drains the payload+LF on normal responses. But it doesn't check the echoed OID, exact field count, or that a `missing` line is an exact complete frame. It depends on a trusted, conforming Git child; malformed **child stdout** is not the same as attacker control of raw blob bytes. Config/try-rev-parse helpers collapse execution failure into “unset/not found”; invalid policy configuration can default when lookup itself fails. Public `real_git`, `cwd`, and directory fields can invalidate `I_repo` after open. **Fix:** use a common hardened Git command constructor for discovery too, pin canonical executable/repo identity, validate exact format/frames/paths, restrict field visibility, distinguish missing from failure, and add recursion detection. Use `--end-of-options` for untrusted rev inputs where supported. The main CLI already excludes leading `-` for its revision position; no general shell injection follows from `rev_parse` alone.

**M6 — Cache invariant fails even in a single process; concurrent repair is unsafe.** `src/cache.rs:65–70,128–153,162–213`; `CONTRACTS.md:118–150`. `HashMap::insert` **replaces** an old digest, but a record is queued only for a previously absent key. A pending record can thus disagree with its map; memory is last-write-wins, disk is first-write-wins for those calls. Public maps also allow mutation without any bookkeeping. **Observed** for blob/tree/commit. Flush checks/repairs length via one handle and later reopens the pathname to append or truncate; no locking coordinates creation, truncate, repair, or `write_all` across processes. A failed validation/open can be treated as “rewrite”; failed writes still clear pending. Best-effort loss on I/O failure is permitted by the text, not crash durability or serializable updates. File APIs follow symlinks; the assumed cache path must be a trusted regular file, not a link, pipe or device. **Fix:** make maps private, use `Entry::Vacant` for documented first-write-wins or implement consistent last-write-wins; lock and validate/repair using one owned file, use exclusive/atomic replacement, propagate serious errors and don't trust disk records for security decisions.

**M7 — Signer I/O, temp files, and process lifecycle.** `src/hooks.rs:63–149,152–164`; `src/git.rs:174–180,244–271`. SSH signing uses PID/time plus `create_dir_all` (not exclusive), default umask, non-exclusive `write`, reads a named `.sig`, and performs best-effort cleanup. On a shared temp root, payload confidentiality and integrity depend on permissions/path ownership; stale paths and symlinks are not ruled out. This is local-filesystem dependent, not remote shell injection. `payload_file.to_str().unwrap()` panics on a non-UTF-8 temp path. Relative key paths depend on process cwd (not necessarily `repo.cwd`); Git's SSH public-key literal/agent/default-key command forms and X.509 signing aren't implemented. For GPG an exit of 0 plus any stdout, even empty, is sufficient; `SIG_CREATED`, format and post-sign verification aren't checked. SSH accepts the analogous empty/invalid signature file from a supposedly successful helper. Both signer selection and key selection come from Git config; configured programs run with the user's authority. Git and GPG pipe writers synchronously write all input **before** draining output; a child that writes enough first can block both sides. Early write errors drop `Child` without a guaranteed wait; there are no timeouts. Batch `Drop` attempts flush/kill/wait, which is better but not a bounded-time guarantee. **Fix:** stream via protected pipes, or create exclusive mode-0700 temp dirs/0600 files with RAII cleanup; use `OsStr` paths, a trusted signer backend matching Git semantics, check signature/status and signer identity, and supervise I/O, cancellation, timeouts and reaping on every path.

**M8 — Git graph validity / termination isn't implied by the Rust traversal.** `src/protocol.rs:171–210,266–313,324–360,539–560,777–794,866–880,931–940`; `src/git.rs:274–289`; `src/main.rs:183–207,264,374–379`. Commit parsing is a buttress-header classifier, not Git's canonical commit parser: it scans all noncontinuation lines, rather than Git's required leading tree/consecutive parent sequence (upstream Git `commit.c:539–557`), doesn't require normal identity headers, and ignores unknown lines. Ambiguous delimiter/malformed reserved header spellings not matching the literal prefixes may be ignored. Tree grammar is uniquely decodable but doesn't reject duplicate names, non-Git modes, reserved path components or bad sorting. One can hash labels for a graph Git considers invalid or interprets differently; a successful `check` is not structural `git fsck --strict` or a filesystem safety check.

Rust detects active tree and all-plain commit cycles and explicitly tracks peeled tags; the sealed BFS uses *visited*, not an acyclicity proof. A cycle crossing a seal is a digest cut for `id`; verification normally fails an edge digest, rather than proving graph acyclicity. I found no unbounded Rust recursion on a finite fixed graph in these loops. **Outside** them, rev expressions and `rev-list` are given to Git first. Stock Git v2.56.1 `tag.c:77–96` and `object-name.c:882–905,961–977` have tag-peeling loops without a visited set. Under the stipulated cyclic store, delegating peeling can hang **before** the Rust guard is reached; Python does this too. No timeout protects the subprocess. **Fix:** constrain input to canonical graph syntax, resolve checked refs/OIDs without implicit Git walks where possible, apply visited/depth/work limits at every peel/walk including helper work. Define whether graph validity beyond digest encoding is required, and do not claim to validate what `id` deliberately doesn't traverse.

### Low

**L1 — `Engine`'s public API doesn't establish its stated invariants.** `src/protocol.rs:15–21,38–50,366–405,425–435,516–541,576–581`. Keys, parsed objects, store and cache are public; cached data is not bound to a store or key set. Even `memory_only` doesn't mean *empty on handoff* if the caller can prepopulate it. A mutable `ObjectStore` has no enforced snapshot/consistent-read property. The digest correctness `ensures` requires the same stable typed map for the lifetime of memoization, canonical keys, and no injected cache entries. On `Err`, completed subresults remain; those are valid only with those preconditions. The documented return of **all** sealed boundary ancestors fails on warm plain-commit cache hits. **Observed:** `frontier-contract.log`. Within one `verify_target` with a fresh engine, previously discovered boundaries in the successful BFS are already queued/visited; this API bug alone is **not** evidence of a skipped ancestor there. **Fix:** encapsulate state, bind caches to immutable snapshots/contexts, and memoize frontier metadata or document results as *newly discovered work* with an explicit caller contract.

**L2 — Writer header grouping and diagnostic data are not byte-safe everywhere.** `src/protocol.rs:964–985`; `src/hooks.rs:232–247,272–292,821–847`; `src/main.rs:391–405`. Signature continuations are dropped as a group, but skipping a BLAKE3 header doesn't set `skip_continuation`; its continuation can be reattached to an unrelated retained header. The writer appends after the entire retained header rather than inserting at a particular committer position; valid ordinary message **bytes are preserved**. The raw first subject line becomes a reflog argument (embedded NUL can cause process creation failure); subjects and other untrusted text are printed without escaping terminal controls. These uses are not shell evaluation. **Fix:** parse/rewrite whole header records, reject illegal continuations for single-line reserved fields, bound/sanitize presentation and reflog text while preserving stored body bytes.

### Informational

**I1 — Hash dependency advisory is real but its failure path isn't reached here.** `Cargo.toml:13–14`, `Cargo.lock:12–38`, `src/protocol.rs:25–32,45–74`, `CONTRACTS.md:104–109`. The lock pins `blake3-servil` and core 0.9.1+metadata to `2c60420c2bccbf6073e35e668691d98520f9b096`. `cargo tree -e features` shows default/`std`, no `zeroize`. The [upstream GHSA-v237-j9h9-8pf7](https://github.com/servil-software-factory/BLAKE3/security/advisories/GHSA-v237-j9h9-8pf7) requires reuse of a wiped hasher and a mixed batch update. Here `ContextKeys` uses `context_key` and one-shot `convenience::hash_with`; upstream `threads/src/lib.rs:204`, `src/convenience.rs:62–66`, `src/lib.rs:1211` re-export and execute the serial derive-key-material path. No such batch/hasher reuse. This is a call-graph conclusion about this build, **not** a blanket clean bill of health. Keep the revision/lock pinned, track upstream advisories and rerun cross-implementation vectors after upgrades/feature unification. A Git SHA-1 dependency pin is not a strong source-authenticity anchor under this audit's own hypothetical break; authenticate/vendor build inputs separately.

**I2 — No direct shell injection established from Git object bytes.** `src/git.rs:235–263,371–378`; `src/hooks.rs:89–99,117–135,290–298,1081–1086,1136–1149,1164–1184`; `buttress-vectors.py:15–20`. Rust uses `Command` with argv; Python uses argv arrays, not `shell=True`. Batch requests contain hex OIDs, not object contents or refname command lines. Hook paths are POSIX single-quoted correctly for non-NUL strings; `"$@"` is quoted; stdin text is passed through a fixed `printf` format, not `eval`. The chained shell buffers all stdin with `$(cat)`, which loses trailing newlines and isn't a binary-safe replay. Trust still extends to PATH/explicit Git, signing programs, configured previous hooks, Git config/environment, OS and filesystem; an attacker who controls one of those executable choices can execute code by design. A normal remote pack is **not** equivalent to control of `.git/config`. No remote-only command execution or memory corruption in the hash primitive was demonstrated. Prefer fixed trusted program paths, length-limited byte forwarding and least-privilege execution.

**I3 — Operational examples describe more than is tested.** `README.md:41–59,163–177,201–210,227–240`; `BUTTRESS.md:210–235`; `tests/integration.rs:187–347,349–451`. The positive clone test uses CLI Git and local fixtures; it doesn't establish all forge, transport or Cargo backend behaviors. `git push --follow-tags` does not generally publish lightweight tags produced by plain `git tag <name>`; tag publication and short-name selection should not be promised universally. The named rebase/cherry-pick test exercises rebase/amend/SSH, not a distinct cherry-pick command. Label examples and external benchmark numbers as such. Specify minimum supported Git/platform and how users can confirm that verification actually ran.

## 4. Remediation sequence and release criteria

1. **Make the verified target unambiguous.** Require canonical Git parsing and a byte-preserving, fully consumed transaction/listing. Separate expected digest provenance from data being checked. Gate release on agreement with stock Git about the object a consumer will actually use.
2. **Make success mean complete success.** Walk ancestor evidence regardless of the root's class; make corruption, missing objects, partial coverage, lack of root evidence, and operational failure distinguishable through every CLI/hook level. Test that no ref disappears from the accounting and strict mode has no silent policy exceptions.
3. **Separate verification, signing and publication.** Use a fresh store view, preserve conflicts as evidence, require signer intent, and publish intended direct refs in a single transaction. Don't issue a signature or immutable pin from an unauthenticated OID cache. Add deterministic multi-worktree/ref-change and I/O-failure tests around each state transition.
4. **Make installation reversible, execution bounded, and the docs literal.** Integrate rather than displace existing hooks; propagate Git configuration/byte argv, enforce resource budgets and supervise children. Keep the independent vector, warm-cache, hook lifecycle, signing-key-selection and coverage tests in CI. A clean run of the six current integration tests is a useful baseline, not evidence these release criteria have been met.
